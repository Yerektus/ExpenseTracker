## 1. Purpose

Expense Tracker is a small educational full-stack app for tracking personal expenses: create,
edit, delete and filter expenses by category, and see per-category totals plus a grand total.
It is the baseline repository for a Software Engineering course, so changes must stay small,
readable and well tested. All data in the repo is fictional.

### Data flow

```
React component ──> src/api.js (fetch, JSON) ──HTTP /api/*──> routers/expenses.py
   ──> Pydantic schemas validate input ──> crud.py ──> SQLAlchemy models ──> SQLite
GET /api/summary: crud.get_summary() ──> list_expenses() ──> calculate_summary() (pure)
```

### Where each kind of logic must live

| Kind of logic | Location | Notes |
|---|---|---|
| Input validation (authoritative) | `backend/app/schemas.py` | amount `> 0`, `Category` enum, description ≤ 255 chars, ISO date |
| HTTP routing, status codes, 404 | `backend/app/routers/expenses.py` | `get_expense_or_404()`; DELETE returns 204 |
| Database access | `backend/app/crud.py` | routers never build SQL queries themselves |
| Business logic (summary) | `crud.calculate_summary()` | pure function, no DB; all categories present, sums rounded to 2 decimals |
| Settings / env vars | `backend/app/config.py` | nothing else reads `os.environ` |
| HTTP calls from the UI | `frontend/src/api.js` | components never call `fetch` directly |
| Category list, labels, colors, formatting | `frontend/src/categories.js` | values must match backend `Category` |
| Client-side validation (UX only) | `validate()` in `ExpenseForm.jsx` | mirrors server rules; the server stays the source of truth |
| Page state and side effects | `frontend/src/App.jsx` | components receive data and callbacks via props |

### Environment variables (all optional)

| Variable | Read in | Default |
|---|---|---|
| `DATABASE_URL` | `backend/app/config.py` | `sqlite:///<repo>/backend/expenses.db` |
| `CORS_ORIGINS` (comma-separated) | `backend/app/config.py` | `http://localhost:5173` |
| `VITE_API_URL` | `frontend/src/api.js` (`import.meta.env`) | `http://localhost:8000` |

Both sides read a single `.env` in the **repository root** (backend via `load_dotenv(PROJECT_ROOT / ".env")`,
frontend via `envDir: ".."`). `.env` is git-ignored; only `.env.example` is committed.

### Test isolation of the database

`backend/tests/conftest.py` creates a fresh SQLite file in pytest's `tmp_path` for **each test**,
overrides the `get_db` dependency via `app.dependency_overrides`, and creates `TestClient(app)`
**without** `with`, so the app lifespan does not run and `backend/expenses.db` is never touched.
Keep it that way: tests must never use the real database.

## 3. Setup

Requirements (from code and installed package metadata):
- **Python ≥ 3.11** (`enum.StrEnum`; FastAPI 0.165 declares `Requires-Python >=3.11`). Verified only on Python 3.14.10.
- **Node.js `^22.12.0 || ^24.0.0 || >=26.0.0`** — required by Vitest 5 (Vite 8 alone accepts `^20.19.0 || >=22.12.0`).
  Note: README says "Node.js 20.19+ or 22.12+", which is not enough for `npm test`. Verified only on Node v26.13.1.

Backend (macOS / Linux; on Windows use `py -m venv .venv` and `.venv\Scripts\Activate.ps1`):

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload          # http://localhost:8000, docs at /docs
```

Frontend (second terminal, backend running):

```bash
cd frontend
npm install
npm run dev                             # http://localhost:5173 (strictPort — must stay 5173 for CORS)
```

Optional demo data: `python seed.py` from `backend/` — **wipes all expenses first** (see §8).

`pip install -r requirements.txt` and `npm install` only install what the manifests already pin.
If `npm install` changes `package-lock.json`, do not commit that change — stop and report it.
(These exact setup commands were not re-run during this audit; the existing `.venv` and
`node_modules` were used.)

## 5. Coding conventions

### General
- Keep changes minimal and focused on the task; match the style of surrounding code.
- Identifiers are English; code comments, docstrings, UI strings and README are **Russian**.
- Only fictional data in code, tests, seeds and fixtures.

### Python (backend)
- Type hints everywhere; SQLAlchemy 2.0 typed style (`Mapped[...]`, `mapped_column`, `select()`).
- Dependencies via `Annotated` (`DbSession = Annotated[Session, Depends(get_db)]`).
- Use `import datetime as dt` (the model and schemas have a field named `date`).
- Validation belongs in Pydantic schemas (`Field(gt=0)`, `max_length`, `Category` enum), not in routers or CRUD.
- Business logic goes into pure, separately testable functions (pattern: `calculate_summary`).
- `PUT` replaces the whole object (`ExpenseUpdate` has the same fields as `ExpenseCreate`).
- No linter is configured: follow PEP 8 and the existing formatting.

### React (frontend)
- JavaScript only (no TypeScript), function components, `.jsx` files, React 19.
- Components get data and callbacks through props; state and side effects live in `App.jsx`.
- All HTTP goes through `src/api.js`, which throws `Error` with a user-readable message.
- Formatting helpers live in `categories.js` (`formatAmount` → `1 234,50`, `formatDate` → `ДД.ММ.ГГГГ`).

### UI library and styling (HeroUI v3 + Tailwind CSS v4)
- **Read [DESIGN.md](./DESIGN.md) before any visual change**, and read the HeroUI docs in
  `.heroui-docs/react/` (index at the end of this file) before using a component — APIs differ
  from HeroUI v2/NextUI. If `.heroui-docs/` is missing, use the type definitions in
  `frontend/node_modules/@heroui/react/dist/` and ask before regenerating the docs (§8).
- Build UI from `@heroui/react` components and their compound parts (`Card.Header`, `Table.Content`,
  `Select.Trigger`, …) before writing custom markup. Icons come from `@gravity-ui/icons`.
- Event and value APIs: buttons use `onPress`; field `onChange` receives the **value**, not an event;
  an empty `NumberField` is `NaN`; dates are `@internationalized/date` values (`parseDate()`, `.toString()` → ISO).
- Button variants by meaning: one `primary` per context, `tertiary` for cancel, `danger` for destructive
  actions, `ghost` for icon-only row actions. Icon-only buttons need `aria-label` (and a `Tooltip`).
- Styling: Tailwind utilities with **semantic HeroUI tokens only** (`bg-background`, `text-foreground`,
  `text-muted`, `bg-accent-soft`, `border-separator`, …). No hex/rgb colors, no `gray-*` palette classes,
  no inline `style`, no new CSS files — `src/index.css` contains only the two imports.
- Dark mode must keep working without per-theme code: never branch on the current theme in components.
  Theme state belongs to `useTheme` in `ThemeSwitcher.jsx`; the inline script in `index.html` mirrors its
  `localStorage` key `heroui-theme` — change both together.
- Feedback patterns already in use: `toast` for successful actions, `Alert` for load errors,
  `Skeleton` while loading, `EmptyState` for empty lists, `AlertDialog` to confirm deletion.

## 6. Test expectations

- **Every change comes with a test.** Backend: add to `backend/tests/test_expenses.py` using the
  `client` and `create_expense` fixtures; pure logic gets a direct unit test (like
  `test_calculate_summary_rounds_totals`). Frontend: add `src/__tests__/*.test.jsx`; mock `../api.js`
  with `vi.mock`, use `@testing-library/user-event` for HeroUI/React Aria fields.
- Before finishing, run **all three**: `pytest -q`, `npm test`, `npm run build`. All must pass, and no
  new warnings beyond the known baseline ones (§4).
- Never delete, skip (`@pytest.mark.skip`, `test.skip`, `.only`), or weaken tests (loosened assertions,
  removed cases, broader mocks) to make a change pass. If a test looks wrong, report it and ask.
- Never report results that were not actually produced. Paste real output. If a command could not be
  run (e.g. Node.js is not installed), say so explicitly instead of assuming it passes.
- Current coverage gaps (for awareness): no frontend tests for `api.js`, `ExpenseList`, `Summary`,
  `ThemeSwitcher`; no backend test for `GET /api/health`.

## 8. Actions requiring human approval

Ask first and wait for an explicit "yes" before:
- **Dependency changes** of any kind (see §7).
- **Database schema changes** (`backend/app/models.py`). There are no migrations: `create_all` creates
  missing tables only and does not alter existing ones, so a schema change also requires recreating
  the local database — a human must decide how.
- **CORS changes** (`CORS_ORIGINS`, `CORSMiddleware` in `main.py`) and the dev port (`vite.config.js`
  `port`/`strictPort` — coupled to the CORS default).
- **API contract changes**: paths, methods, status codes, request/response fields in `schemas.py` and
  `routers/expenses.py`, and their consumer `src/api.js`. Also adding/removing categories (backend
  `Category` and frontend `categories.js` must change together).
- **Deleting or renaming files.**
- Renaming or adding environment variables (and `.env.example`).
- Running `python seed.py` (it deletes every expense in the configured database).
- Regenerating the HeroUI docs (`npx heroui-cli@latest agents-md --react --output AGENTS.md`):
  it downloads from the network and rewrites this file — **(unverified)** whether it preserves the
  sections outside the markers.
- Any network download or tool installation not covered above.
